What “done-for-you” means here

The DFY offer is meant to reduce friction for the buyer. Instead of only giving strategy documents, this tier adds the implementation path and service layer.

  1. Environment readiness: the buyer’s hosting and deployment stack are prepared once the required account details are available.
  2. Domain path: the chosen domain is used for the live offer or project setup.
  3. API path: the buyer’s chosen AI provider keys are connected into the workflow so the stack runs on the buyer’s own provider access.
  4. Model blueprint deployment: the product structure is prepared according to the Empire scope.
  5. Annual continuity: the offer includes continuing updates and annual support during the subscription term.

Important: this is still dependent on the buyer providing their own accounts, APIs, and required access. The service handles the setup path, but it cannot replace the buyer’s ownership of their domain, API usage, GitHub, Vercel, or related accounts.

Exactly what the buyer must provide

To start the DFY annual setup, the buyer needs to provide the following. This section is intentionally explicit so nothing slows down the onboarding process.

The buyer must provide whichever API they want used for the stack. OpenAI, xAI, Claude, or another supported provider can be used. The goal is simple: the stack must be able to authenticate against the model provider the buyer chooses.

  • At least one usable AI API is required

Notes — record provider names, key ownership, account email, intended usage, and any limits to respect

Chapter 2 — Domain to deploy on

The buyer needs to provide the domain they want the product or offer to use. This is necessary for live deployment, routing, and future brand continuity.

Chapter 3 — Hosting account name and email

The buyer needs to provide the name and email for the hosting account. These can be updated later, but they are needed to begin setup cleanly.
